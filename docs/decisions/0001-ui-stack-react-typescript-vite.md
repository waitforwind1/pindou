# ADR-0001：UI 技术栈采用 React + TypeScript + Vite

- 状态：Accepted（设计基线）
- 日期：2026-11-06
- 关联：`docs/architecture.md` 第 2.1、5、7 节

## 背景

本项目是一个单页桌面创作工作台，包含上传、参数草稿、已生成图纸、异步生成/导出、错误态、P1 编辑和撤销等状态。图纸绘制本身由 Canvas 承担，React 不参与逐格像素绘制。

需要判断 React 是否真的比原生 TypeScript、Preact、Svelte、Solid 或 Vue 更适合 72 小时交付。

## 可选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| React + TypeScript + Vite | 状态/组件模型成熟；类型和测试生态完整；团队最容易复用经验 | 约 50 KB 级运行时；单页工具有框架抽象成本 | 采用 |
| Vanilla TypeScript + Vite | 依赖最少、运行时最小 | 复杂交互、焦点管理、异步状态和可访问性容易手写失控 | 不采用 |
| Preact | 接近 React，包更小 | 兼容层不是本项目核心收益；团队熟悉度/生态有额外风险 | 不采用 |
| Svelte | 响应式简单、运行时小 | 必须重新建立团队模式；没有解决本项目独有算法问题 | 可选替代，不采用 |
| SolidJS | 细粒度性能好 | 生态和排障经验相对少；Canvas 已承担重绘，收益有限 | 可选替代，不采用 |
| Vue | 组件和表单体验成熟，生态完整 | 与 React 同等级，不构成必须迁移的理由 | 可选替代，不采用 |

## 决策

采用 React + TypeScript（严格模式）+ Vite。

- 状态使用 React 内置 `useReducer` + 单一 Workspace store；不引入全局状态库。
- 样式原定为原生 CSS Custom Properties + CSS Modules；P04 初始化按用户确认的技术栈改为 Tailwind CSS v4，详见 ADR-0010。仍不引入 UI 组件框架。
- 路由、SSR、Next.js 和后端渲染均不引入。
- TypeScript 开启 `strict`；领域核心不依赖 React 类型。

## 理由

1. 本项目的主要 UI 风险不是渲染速度，而是“草稿参数 / 已生成图纸 / 旧版本 / 导出快照 / 编辑状态”容易分叉。React 的显式状态和组件边界更便于审查。
2. Canvas 已经承担高频绘制，React DOM 只更新面板和清单；框架性能差异不是决定性因素。
3. TypeScript 对色盘索引、空位、导出选项和异步状态有直接保护价值。
4. Vite 提供足够快的最小构建链；无 SSR、服务端路由或后端运行时。
5. 若团队对 Vue/Svelte 更熟，仍可采用同一分层架构；React 不是不可替换的领域依赖。

## 代价与限制

- 增加框架运行时和组件抽象；对 72 小时而言可接受。
- React Context 可能在 P1 编辑/选择态频繁更新时造成重渲染；先用 selector 和分层 Canvas 控制，实测后再引入小型 store。
- 不在 `useEffect` 中隐式启动生成；生成由明确用户动作和服务编排触发，避免严格模式重复副作用。
- UI 组件不得自行计算颜色匹配、数量或 PNG 内容；这些必须通过领域核心/应用服务。

## 验证方式

- 纯核心在 Node/Vitest 中运行，不 import React。
- P0 三栏工作台在 1440×900 和 1280×800 完成一次全流程。
- 若 React 层在 16,384 格编辑测试中产生不可接受掉帧，问题优先定位到 Context/选择器，而不是直接换框架。
