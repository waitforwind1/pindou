# ADR-0007：P0 不使用 Web Worker，保留可替换边界

- 状态：Accepted（设计基线）
- 日期：2026-11-06
- 关联：`docs/architecture.md` 第 2.6、8 节；FR-04、FR-06、FR-15

## 背景

图片采样和 67 色匹配可能阻塞主线程。但 P0 只有 32/48/64 预设，64×64 最多 4,096 格；逐格对 67 色做 ΔE76 约 274,432 次距离计算。引入 Worker 会增加线程通信、取消、错误序列化和构建配置成本。

## 可选方案

| 方案 | 主线程风险 | 工程成本 | 可测试性 | 结论 |
| --- | --- | --- | --- | --- |
| P0 主线程纯核心 | 64×64 通常可控；大图/照片模式可能变慢 | 最低 | 核心函数直接单测 | **P0 采用** |
| 一开始全部搬进 Worker | 最低 | 中高；UI/Worker 状态同步复杂 | Worker 边界增加测试成本 | 不采用 |
| 主线程 + 条件 Worker | 可控 | 中；保留同一接口 | 可分别测试主线程/Worker 实现 | **P1/P2 采用条件** |
| 后端处理 | 不占本地 CPU | 需服务、上传、隐私、网络 | 与纯前端冲突 | 不采用 |

## 决策

- P0 使用主线程 `GenerationService` 实现。
- 领域核心保持纯函数、无 DOM/React 依赖；`GenerationService` 是可替换接口。
- 只有以下任一情况出现时，才引入 Worker：
  - 128×128 + 区域平均/CIEDE2000/多品牌重映射使 p95 生成超过 150-200 ms；
  - 性能测试出现明显长任务或用户交互掉帧；
  - 需要真正中止正在运行的大计算。
- 若引入 Worker，只移动采样/匹配/构建等 CPU 核心，不移动 React，也不把主预览 Canvas 放在 Worker。
- Worker 结果通过 `stateVersion`/`requestId` 与当前快照对齐；旧任务被终止或丢弃。

## 理由

1. P0 计算规模在桌面浏览器中通常不需要线程化；先做 Worker 会增加大量与核心目标无关的风险。
2. 纯核心 + 服务接口让 Worker 成为适配器替换，而不是架构重写。
3. 生成前后保留绘制机会和忙碌状态可满足短任务的反馈需求。
4. 未来扩展到 128×128 照片模式时，有明确触发条件，不凭感觉优化。

## 代价与限制

- P0 极端大图或慢设备上可能短暂阻塞主线程；用输入上限、阶段反馈和性能测试控制。
- 主线程无法真正中止同步循环；P0 通过请求序号忽略旧结果，Worker 阶段才做真正取消。
- 如果性能实测提前超过阈值，可在完成 P0 后加入 Worker，但不能牺牲 P0 验收。

## 验证方式

- 64×64 典型样本生成时按钮状态可见、页面不白屏。
- 连续切换参数不会让旧结果覆盖新结果。
- 若启用 Worker，Worker 与主线程实现对同一输入产生逐格一致的索引。
