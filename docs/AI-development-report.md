## 1. 项目背景与需求理解

我希望完成的不是一个普通的“把图片变成马赛克”的网页，而是一个能够指导实际摆放实体拼豆的生产图纸工具。用户上传图片后，系统需要读取图片像素，按照目标网格尺寸进行采样，把有效像素匹配到真实市场品牌色盘中的颜色和色号，最后生成带有网格线、逐格色号、坐标、颜色图例和材料数量的图纸。

我将原题拆成了三层：

- P0：图片上传与处理、真实品牌基础色盘、实体颜色匹配、图纸生成、可下载导出。这些功能不能删除、弱化或改成可选。
- P1：材料用量统计、自定义图纸尺寸、大图分板。这些功能直接影响用户采购和实际制作，因此纳入本次交付。
- P2：第二品牌、品牌重映射、PDF/SVG、单格编辑、撤销重做、工程文件保存恢复等。由于 72 小时限制和数据真实性风险，本次明确延期或移除。

我特别冻结了几个关键口径：

1. 透明像素不是白色拼豆。`A < 128` 必须表示为空位 `null`。
2. `A >= 128` 的半透明像素在白底上合成后再匹配。
3. 色盘必须是真实品牌色盘，色号和名称可核验。
4. 参考 RGB 只能称为官方色卡派生参考值，不能伪称为官方 RGB。
5. 预览、统计和导出必须使用同一份 `PatternDocument`。
6. PNG 必须脱离网页独立阅读，而不是简单截图网页。

## 5. 两个最大难点和解决过程

### 难点一：如何保证色盘是真实可核验的，而不是“看起来像真的”

#### 问题背景

拼豆图纸最终要指导购买和摆放实体材料。如果我只给 AI 一个“常见拼豆颜色数组”，很容易出现虚构色号、混用不同品牌编号、把第三方网站颜色值称为官方 RGB 等问题。这会直接破坏 P0 的真实性要求。

#### 我最初的 Prompt

我最初要求 AI：

> 首先选择一个市场上真实存在的拼豆品牌，优先考虑 Perler 或 Artkal；找到可核验的真实基础色盘，记录品牌、系列、色号、名称和对应颜色值；不得编造品牌、色号或官方数据。

#### 我发现的问题

仅仅要求“找一个真实色盘”还不够，因为：

- 官方色卡通常提供色号和名称，但不一定提供可直接用于程序的 RGB 标准。
- 屏幕显示值、PDF 渲染值和实体塑料颜色不是同一个概念。
- 如果颜色表没有 checksum 和来源记录，后续代码可能静默替换数据。

#### 我补充的上下文和约束

我进一步明确要求 AI：

1. 将官方色号、英文名称和派生 RGB 分成不同可信等级。
2. 为每个颜色记录来源文档、页码、行列位置和采样方式。
3. 在运行时校验颜色数量、唯一性、RGB 范围、来源字段和 canonical checksum。
4. UI 和导出必须说明“RGB 为官方色卡派生参考值，不代表官方 RGB 标准”。
5. 色盘校验失败时禁止继续匹配。

#### 最终解决方案

项目采用 Hama 2026 Midi Solid 67 色。色号和英文名称来自官方 Hama Midi 色卡；RGB 是使用官方 PDF 栅格化后从色豆区域采样得到的参考值，并明确标注为派生数据。色盘快照、来源审计和运行时仓库校验分别位于：

- `src/palettes/hama-midi-solid-2026.palette.json`
- `src/palettes/hama-midi-solid-2026.source.json`
- `src/palettes/repository.ts`
- `docs/palette-sources.md`

#### 验证

我让 AI 使用 Vitest 检查 67 个唯一色号/名称、RGB 范围、来源字段、PDF SHA-256 和 canonical checksum。最终没有把“颜色近似值”写成官方 RGB，也没有使用未经核验的 Perler/Artkal 色号。

### 难点二：画布滚轮缩放与网页滚动冲突

#### 问题背景

完成工作台后，我实际使用发现：鼠标在中间图纸区域滚轮时，图纸会缩放，但整个网页也会上下移动。用户很难在大图上精确查看局部内容。

#### 我最初的实现

原组件使用 React `onWheel`：

- 根据 `deltaY` 修改 zoom。
- 调用 `event.preventDefault()`。
- 只保存 zoom，不保存指针锚点对应的平移量。

静态看起来逻辑完整，但实际浏览器行为仍然出现页面滚动冲突，而且缩放时鼠标所在内容会发生明显偏移。

#### 我调整后的 Prompt

我没有要求 AI 重写整个画布，而是提供了具体的浏览器事件上下文：

> 请检查当前图纸预览组件中的 wheel 事件监听逻辑。优先通过正确处理 WheelEvent、阻止图纸区域内的浏览器默认滚动行为来解决。注意 React 事件监听的 passive 配置问题：如果使用原生事件监听，需要确保监听器允许调用 preventDefault()。只在图纸预览区域内阻止默认滚动，不要在整个页面或全局 document 上禁用滚轮事件。缩放应以鼠标当前位置为中心，保留现有缩放范围和其他交互。

#### 最终解决方案

AI 先检查了 `src/components/PatternCanvas.tsx` 和 `src/render/viewport.ts`，发现项目中其实已有 `zoomAroundPoint` 函数，只是原组件没有使用它。

最终方案是：

1. 在画布容器上用 `addEventListener('wheel', handler, { passive: false })`。
2. 只对画布容器内的事件调用 `preventDefault()`。
3. 使用容器 `getBoundingClientRect()` 将鼠标坐标转换成画布局部坐标。
4. 调用 `zoomAroundPoint` 同时计算新的 zoom 和 pan。
5. 在 cleanup 中移除同一个监听器，避免重复绑定。
6. 不触碰全局 `document` 或页面其他区域的滚轮行为。

#### 验证

我新增了 Playwright E2E：鼠标移动到图纸区域，滚轮后缩放比例从 100% 变为 110%，同时断言 `window.scrollY` 不变。Chrome 和 Edge 均通过，当前 E2E 共 8 项通过。

我认为 AI 对本项目最有价值的地方不是“自动写出所有代码”，而是把跨领域要求快速转成可执行的工程约束：

- 帮我把原题拆成需求、用户故事、验收标准和任务依赖。
- 帮我比较技术方案，暴露 Canvas 导出、颜色空间和数据源一致性风险。
- 快速搭建纯函数算法和测试骨架，使我可以把注意力放在规则正确性上。
- 根据我提供的浏览器现象和事件约束定位具体组件问题。
- 协助维护 README、任务台账、验收矩阵和 AI 记录，减少代码与文档脱节。

## 8. AI 使用局限与人工审查

我没有把 AI 输出直接视为事实。色盘真实性必须由我核对官方来源、PDF 和采样记录；AI 不能替代品牌数据审计。

我也没有把“代码看起来正确”当作浏览器行为验证。滚轮冲突、真实下载、Chrome/Edge 兼容性等问题必须通过实际运行和 Playwright 验证。

我重点人工审查了以下内容：

- 空位是否严格使用 `null`，没有错误映射成白色拼豆。
- 每个有效 `colorIndex` 是否存在于当前已校验色盘。
- 统计、预览、图例和导出是否来自同一个 `PatternDocument`。
- 分板是否存在遗漏、重复和数量不守恒。
- 导出是否为独立重绘，而不是网页截图。
- 测试结果是否来自实际执行命令。
